# JLUXE — Phase 6: CMS + Database
## GitHub Copilot / AI Coding Agent Implementation Specification

> **Project:** JLUXE Developers Website  
> **Phase:** 6 — CMS + Database  
> **Status:** NEXT IMPLEMENTATION PHASE  
> **Scope:** Data-driven content architecture and persistence layer  
> **Previous Phase:** Phase 5 — Real Estate Projects & Properties  
> **Out of Scope:** Lead CRM, enquiry management, site-visit scheduling, admin dashboard

---

# 1. PURPOSE

Phase 6 converts the JLUXE website from a frontend driven primarily by static content/data into a **data-driven website architecture**.

The goal is to establish:

```text
CMS / Database
      ↓
Data Access Layer
      ↓
Application Routes
      ↓
Reusable UI Components
```

Phase 5 established the frontend/domain architecture for:

- Real Estate
- Projects
- Properties
- Plots

Phase 6 now introduces persistent content models and a clean data-access layer so that future phases can consume the same architecture.

---

# 2. CRITICAL IMPLEMENTATION RULE

Before changing anything:

1. Inspect the complete existing repository.
2. Review Phase 1–5 implementation.
3. Identify existing static data structures.
4. Preserve completed UI and routing.
5. Do not rewrite working frontend components unnecessarily.
6. Replace static data progressively through a data-access layer.
7. Do not couple UI components directly to database queries.
8. Do not expose database credentials to the browser.
9. Do not invent real JLUXE business information.
10. Use seed/demo records only where actual source data is unavailable.
11. Clearly distinguish seed/demo records from verified business content.
12. Run build/type checks after each major architectural change.

```text

      ↓
Database Query
```

```text

      ↓
Server/Data Loader
      ↓
Repository / Data Access Layer
      ↓
Database
```

```text
UI
 ↓
Domain/Data Access
 ↓
Database
```

The frontend should not know implementation details of the database.

# 6. DATABASE TECHNOLOGY

Inspect the existing project before selecting or changing the database technology.

If the repository already contains a database abstraction, reuse it.

If a database technology has not yet been established, use the simplest production-appropriate solution compatible with the existing TanStack Start architecture and deployment target.

Do not introduce multiple database technologies.

The implementation must support:

- local development
- environment-based connection configuration
- migrations/schema management
- seed data
- server-side access

Database credentials must never be committed to Git.

- do not expose stack traces

# 66. PHASE 6 END STATE

The desired architecture is:

```text
                    JLUXE WEBSITE
                          │
             ┌────────────┴────────────┐
             │                         │
        Public Routes             Future Admin
             │                         │
             ▼                         ▼
      Server/Data Layer        Future Admin Layer
             │                         │
             └────────────┬────────────┘
                          ▼
                   Repository Layer
                          │
                          ▼
                     Database
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
   Ecosystems          Services        Real Estate
                                      │
                             ┌────────┼────────┐
                             │        │        │
                          Projects Properties Plots
```

The key objective is **not simply adding a database**.

The objective is creating a maintainable content architecture where:

```text
Content
   ↓
Database
   ↓
Repository
   ↓
Routes
   ↓
Reusable Components
   ↓
JLUXE Website
```

can scale into the CMS, lead-management and admin phases without requiring another major architectural rewrite.

**Phase 6 goal:**

> Establish a secure, structured, CMS-ready database and data-access foundation while preserving the completed JLUXE frontend and keeping future CRM/admin functionality strictly separated into later phases.
